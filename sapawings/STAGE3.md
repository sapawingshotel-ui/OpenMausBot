# Stage 3 — brand memory and targeted dependency patch

Date: 2026-11-11. Deployment remains paused. No publishing or PMS changes.

## Operator-managed brand memory

`brand_memory.py` implements a private, versioned SQLite evidence store with four brand namespaces. Each card has a kind, status, source and observation time. Verified cards require an operator review record. Volatile facts (prices, policy, inventory and events) require an expiry; expired facts are excluded. Provisional, disputed and historical cards remain visible as exclusions, not usable facts. Asset verification additionally requires a checksum and confirmed rights; verified learnings require measurement references. None of those fields proves a source is true: the trusted operator must review it. External text cannot grant tools or permissions.

Updates append versions with an expected-version check. Retrieval uses only the newest card per key; superseding a verified fact with a disputed card removes it from the usable context. Old records remain as history. Historical evidence can be observed after its original expiry without being promoted to current truth.

`build_brief` returns a snapshot, evidence references, required bilingual/editable outputs and QC checks. It does not call a model. When TaskStore is configured with a trusted memory store, task creation/revision requires an exact snapshot. Completion, QC and publishing preflight recheck it. Context changes, expiry or tampering force revision/re-QC; detaching the store cannot make a snapshot-bearing task pass. Earlier legacy tasks without memory remain supported only by the non-memory configuration; that configuration must never be exposed as a fallback to deployed workers.

The memory DB and task DB are separate local SQLite connections: checks are not an atomic cross-database transaction. Concurrent operator edits can race with a boundary check. A live publishing service must serialize memory revisions with the action authorization/write, or move them into one transactional store and recheck immediately before provider submission. No live publication exists here, so this is a deployment requirement rather than a claimed solved boundary.

This is explicit evidence retrieval, not model fine-tuning or automatic learning. The operator API is trusted setup, not a worker-facing permission API. Same-process/filesystem limitations from stage 2 apply. A fixed forbidden-field check is not comprehensive PII detection. Do not put raw guest records, secrets or irrelevant personal information into memory.

## Dependency tracing

`dependency_paths.json` traces all 17 affected locked package versions to importer roots across the three workspaces. Paths are shortest declared snapshot paths per importer/root group. Optional edges can be platform-inactive; development/build reachability is not production exploitability. This analysis identifies upgrade locations without blanket major-version overrides.

Prepared a focused root runtime change: **undici 8.11.2 → 8.12.2**. The maintainer release notes explicitly describe security fixes; npm metadata provides the exact new integrity and unchanged Node engine requirement. Both old/new lock snapshots have no dependency edges. Updated root package manifest, root importer, package integrity and snapshot key. Parsed YAML structures were compared: unrelated structures are unchanged. No upstream package, installer, hook or build script ran. The lockfile edit was targeted rather than regenerated by pnpm, so frozen-install and runtime compatibility validation remain pending.
